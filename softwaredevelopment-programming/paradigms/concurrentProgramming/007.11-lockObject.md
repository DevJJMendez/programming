# Objetos de Bloqueo
Los objetos de bloqueo (lock objects) son herramientas de sincronización en la programación concurrente que controlan el acceso a recursos compartidos. En lugar de permitir que múltiples hilos accedan simultáneamente a un recurso, los objetos de bloqueo aseguran que solo un hilo pueda acceder a dicho recurso a la vez, mientras que otros hilos deben esperar a que el bloqueo sea liberado.

En Java, el bloqueo implícito (a través de la palabra clave synchronized) y el bloqueo explícito (a través de clases como ReentrantLock) son las formas más comunes de gestionar la sincronización en programas concurrentes.

## ¿Para qué sirven los Objetos de Bloqueo?
1. **Controlar el acceso a recursos compartidos**:
   * Los objetos de bloqueo aseguran que solo un hilo pueda ejecutar una sección crítica del código a la vez, evitando que múltiples hilos modifiquen o accedan a datos compartidos simultáneamente.

2. **Evitar problemas de concurrencia**:
   * Ayudan a prevenir problemas como race conditions, donde el resultado de un programa cambia según la interleaving (intercalado) de los hilos, y deadlocks, donde los hilos se bloquean entre sí esperando que el otro libere un recurso.

## ¿Qué resuelven los Objetos de Bloqueo?
1. **Race Conditions (Condiciones de Carrera)**:
   * Situaciones donde múltiples hilos acceden a un recurso compartido y el resultado depende del orden en que se ejecutan los hilos. Los objetos de bloqueo garantizan que un recurso compartido solo sea manipulado por un hilo a la vez, eliminando la incertidumbre en el acceso concurrente.

2. **Problemas de Consistencia de Datos**:
   * Los objetos de bloqueo aseguran que las operaciones críticas (como la lectura y escritura en un recurso compartido) se ejecuten de manera atómica, evitando inconsistencias y errores.

3. **Coordinación y Señalización entre Hilos**:
   * Permiten que los hilos se sincronicen entre sí, haciendo que esperen o se despierten bajo ciertas condiciones.

## ¿Cómo lo resuelven?
Los objetos de bloqueo controlan el acceso a los recursos compartidos de las siguientes maneras:

1. **Adquisición y Liberación del Bloqueo**:

   * **Adquisición**: Un hilo adquiere el bloqueo antes de acceder a la sección crítica del código. Esto asegura que ningún otro hilo pueda entrar en la sección crítica hasta que el bloqueo sea liberado.

   * **Liberación**: Después de que el hilo termina de usar el recurso compartido, libera el bloqueo, permitiendo que otros hilos lo adquieran.

2. **Bloqueos Implícitos (synchronized)**:

   * En Java, la palabra clave synchronized es un tipo de bloqueo implícito que asegura que el acceso a la sección de código o método esté controlado de manera automática. Cuando un hilo entra en una sección synchronized, otros hilos deben esperar a que ese hilo termine.

3. **Bloqueos Explícitos (`ReentrantLock`, `ReadWriteLock`)**:

   * Proporcionan un mayor control sobre la sincronización. Por ejemplo, `ReentrantLock` ofrece funcionalidades adicionales como intentar adquirir un bloqueo sin esperar, interrupciones de adquisición de bloqueo, y tiempos de espera.

## Tipos Comunes de Objetos de Bloqueo en Java
1. **`synchronized` (Bloqueo Implícito)**:

   * Fácil de usar, pero limitado en funcionalidad. No ofrece un control detallado sobre las condiciones de espera o el monitoreo del estado del bloqueo.

   * **Ejemplo**:

```java
public synchronized void metodoCritico() {
    // Código que solo un hilo puede ejecutar a la vez
}
```

2. **`ReentrantLock` (Bloqueo Explícito)**:

   * Ofrece más flexibilidad que synchronized. Se debe adquirir y liberar manualmente, proporcionando métodos como tryLock() para intentos no bloqueantes y lockInterruptibly() para bloquearse hasta que se libere el bloqueo o se interrumpa el hilo.

   * **Ejemplo**:

```java
ReentrantLock lock = new ReentrantLock();

lock.lock();
try {
    // Código que solo un hilo puede ejecutar a la vez
} finally {
    lock.unlock();
}
```

3. **`ReadWriteLock` (Bloqueo de Lectura/Escritura)**:

   * Permite múltiples lectores simultáneos (hilos que solo leen el recurso), pero restringe el acceso exclusivo a los escritores (hilos que modifican el recurso). Esto es útil cuando las operaciones de lectura son más frecuentes que las de escritura.
   
   * **Ejemplo**

```java
ReadWriteLock rwLock = new ReentrantReadWriteLock();
Lock readLock = rwLock.readLock();
Lock writeLock = rwLock.writeLock();

readLock.lock(); // Adquirir para lectura
try {
    // Código de solo lectura
} finally {
    readLock.unlock(); // Liberar el bloqueo de lectura
}

writeLock.lock(); // Adquirir para escritura
try {
    // Código que modifica el recurso
} finally {
    writeLock.unlock(); // Liberar el bloqueo de escritura
}
```
