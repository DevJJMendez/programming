# Nomenclaturas
Las reglas de nomenclatura en bases de datos juegan un papel clave para mantener un sistema ordenado, legible y fácil de mantener, sobre todo cuando los proyectos crecen en complejidad. PostgreSQL no es la excepción, y seguir buenas prácticas de nomenclatura es esencial para construir bases de datos robustas y escalables.

## Principios Generales de Nomenclatura
1. **Consistencia**: Sigue un esquema de nombres uniforme a lo largo de la base de datos. Es más importante que los nombres sean consistentes que una convención específica.

2. **Legibilidad**: Utiliza nombres claros y descriptivos que hagan fácil entender el propósito del objeto (tabla, columna, índice, etc.).

3. **Uso de snake_case**: En PostgreSQL es común usar `snake_case` (palabras separadas por guiones bajos) para nombrar los objetos, ya que los nombres de objetos distinguen entre mayúsculas y minúsculas, y esto evita problemas al hacer consultas.

### Nomenclatura para bases de datos
* El nombre de la base de datos debe reflejar claramente su propósito o el sistema al que pertenece.

* Evita nombres genéricos como `db`, `data`, o `test`, que no dicen nada sobre el contenido o propósito.

* **Ejemplo**:
   * Para una base de datos de un sistema de gestión de ventas, un nombre como `sales_management_db` es más adecuado que solo `sales_db`.

* Evita el uso de caracteres especiales (como -, @, !) y mayúsculas, ya que PostgreSQL es sensible a mayúsculas y minúsculas.

* Usa solo letras, números y guiones bajos (_).

* Ejemplo: `inventory_management` en lugar de `Inventory-Management!`.

* Prefijos o Sufijos Opcionales:

  * Si administras múltiples bases de datos en un servidor, puedes agregar prefijos o sufijos para distinguir entre entornos o sistemas.

  * Ejemplos:
    * Prefijo para ambiente de desarrollo: `dev_erp_system`.

    * Sufijo para identificar el ambiente de producción: `erp_system_prod`.

* Reflejar el entorno (opcional):

  * Si es necesario distinguir entre entornos (desarrollo, pruebas, producción), puedes incluir una parte en el nombre que indique el ambiente.

  * Ejemplos:
    * `app_production_db`

    * `app_staging_db`

    * `app_development_db`

### Nomenclatura de Tablas
Las tablas suelen representar entidades del mundo real (productos, usuarios, pedidos). Para nombrarlas, sigue estas pautas:

* **Nombres en plural**: Usar nombres en plural permite que quede claro que la tabla contiene múltiples registros. Ejemplo: `products`, `customers`.

* **Descriptivos y claros**: Usa nombres que describan claramente el contenido de la tabla. Ejemplo: `order_items`, `employee_salaries`.

* **Snake_case**: Separar palabras con guiones bajos en lugar de usar **camelCase** o **PascalCase**. Ejemplo: `customer_orders`, `user_profiles`.

Ejemplo
```sql
CREATE TABLE users (
    user_id SERIAL PRIMARY KEY,
    first_name VARCHAR(100),
    last_name VARCHAR(100),
    email VARCHAR(100) UNIQUE,
    created_at TIMESTAMP
);

CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    user_id INT REFERENCES users(user_id),
    order_date DATE,
    total_amount DECIMAL(10, 2)
);
```

### Nomenclatura de Campos/Columnas
Las columnas representan atributos de las entidades, y deben nombrarse para describir claramente el dato que almacenan:

* **Nombres en singular**: A diferencia de las tablas, los nombres de las columnas suelen estar en singular, ya que representan un solo atributo. Ejemplo: `first_name`, `order_date`.

* **Prefijos o sufijos opcionales para claves foráneas**: Las columnas que son claves foráneas pueden incluir el nombre de la tabla referenciada o usar un sufijo como `_id`. Ejemplo: `user_id` para una clave foránea que referencia a `users`.

Ejemplo
```sql
CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,
    product_name VARCHAR(255),
    price DECIMAL(10, 2),
    stock_quantity INT
);
```
### Nomenclatura de Claves Primarias
Para las claves primarias, sigue estas pautas:

* **Formato estándar**: Usa `nombre_tabla_id` como el nombre de la clave primaria de cada tabla. Esto ayuda a identificar de inmediato la columna como clave primaria y su relación con la tabla.

* No usar nombres genéricos como `id`, ya que puede ser confuso en queries con múltiples joins.

Ejemplo
```sql
CREATE TABLE customers (
    customer_id SERIAL PRIMARY KEY,
    customer_name VARCHAR(255),
    email VARCHAR(255)
);
```

### Nomenclatura de Claves Foráneas
Las claves foráneas son referencias a columnas en otras tablas, y deben ser claras en su función:

* Agregar el sufijo `_id` al nombre del campo de clave foránea que referencia la columna clave primaria. Esto facilita la comprensión de las relaciones.

* **Opcional**: Usar prefijos con el nombre de la tabla referenciada para mejorar la claridad si hay múltiples claves foráneas.

Ejemplo
```sql
CREATE TABLE orders (
    order_id SERIAL PRIMARY KEY,
    customer_id INT REFERENCES customers(customer_id),  -- clave foránea clara
    order_date TIMESTAMP
);
```

### Nomenclatura de Índices
Los índices permiten optimizar el acceso a los datos. La convención más común es incluir el nombre de la columna o columnas que se están indexando y usar el prefijo `idx_`.

Ejemplo
```sql
CREATE INDEX idx_users_email ON users(email);

CREATE INDEX idx_orders_order_date ON orders(order_date);
```

### Nomenclatura de Constraints (Restricciones)
Las restricciones en PostgreSQL aseguran la integridad de los datos, y pueden ser clave primaria, clave foránea, **UNIQUE**, **CHECK**, entre otras.

* **PRIMARY KEY**: Usa el formato `pk_nombre_tabla`. Ejemplo: `pk_users`.

* **FOREIGN KEY**: Usa el formato `fk_nombre_tabla_columna`. Ejemplo: `fk_orders_customer_id`.

* **UNIQUE**: Usa el formato `uk_nombre_tabla_columna`. Ejemplo: `uk_users_email`.

Ejemplo
```sql
ALTER TABLE orders ADD CONSTRAINT fk_orders_customer_id FOREIGN KEY (customer_id) REFERENCES customers(customer_id);
```

### Nomenclatura de Vistas
Las vistas suelen representar consultas predefinidas, y por convención es recomendable que el nombre de la vista comience con el prefijo `view_`.

**Ejemplo**
```sql
CREATE VIEW view_active_users AS
SELECT user_id, first_name, last_name FROM users WHERE is_active = true;
```

### Nomenclatura de Funciones y Triggers
Para las funciones, el nombre debe reflejar la acción que realiza y el objeto sobre el que trabaja. Para los triggers, usa prefijos como `trg_` y detalla la tabla y evento asociado.

Ejemplo para funciones
```sql
CREATE FUNCTION calculate_total_price(order_id INT) RETURNS DECIMAL AS $$
BEGIN
    -- Lógica de la función
END;
$$ LANGUAGE plpgsql;
```

Ejempo para triggers
```sql
CREATE TRIGGER trg_update_stock 
AFTER INSERT ON order_items 
FOR EACH ROW 
EXECUTE FUNCTION update_product_stock();
```

## Buenas prácticas adicionales
* **Evitar abreviaturas ambiguas**: Usa nombres completos y descriptivos. Evita abreviaturas a menos que sean ampliamente comprendidas (como `qty` para cantidad).

* Mantener la longitud razonable: Los nombres deben ser descriptivos pero no demasiado largos. A menudo, 2-3 palabras son suficientes para expresar el propósito de una columna o tabla.

* **No usar palabras reservadas**: Evita nombres de tablas o columnas que sean palabras reservadas en SQL (ejemplo: `select`, `group`).
