# `@Injectable`
`@Injectable` es un decorador en Angular que marca una clase como un servicio o proveedor que puede ser inyectado a través del sistema de inyección de dependencias (**DI, Dependency Injection**) de Angular.

Es una pieza clave para habilitar la inyección de dependencias en Angular, ya que informa al framework que esta clase puede ser utilizada como dependencia en otros componentes, servicios o directivas.

## ¿Para qué sirve @Injectable?
* Habilitar la inyección de dependencias: Marca la clase como un servicio que Angular puede inyectar automáticamente cuando se requiere.

* Declarar dependencias necesarias: Permite que la clase consuma otras dependencias a través de su constructor.

* Configurar el ámbito del servicio: En combinación con la propiedad providedIn, define cómo y dónde estará disponible el servicio.

* Habilitar servicios reutilizables: Facilita la creación de servicios reutilizables que pueden compartirse en toda la aplicación o en módulos específicos.

## ¿Qué resuelve?
Problemas que resuelve:

* Instanciación manual de servicios: Sin @Injectable, habría que crear manualmente instancias de los servicios y gestionar su ciclo de vida, lo cual es tedioso y propenso a errores.

* Dependencias no configuradas: Antes de @Injectable, era necesario declarar explícitamente todas las dependencias, lo que complicaba el mantenimiento.

* Gestión de alcance: Ayuda a definir si un servicio estará disponible globalmente, solo en un módulo, o incluso de forma limitada a componentes específicos.

## ¿Cómo lo resuelve?
Angular resuelve estos problemas de la siguiente manera:

* Sistema de inyección de dependencias: Angular detecta las clases decoradas con @Injectable y las registra en su sistema DI para proporcionar instancias automáticamente cuando se solicitan.

* Declaración de dependencias: Mediante el constructor, @Injectable permite que un servicio reciba otras dependencias automáticamente.

* Optimización de ámbito: Usando providedIn, optimiza la carga y el alcance de los servicios para evitar cargas innecesarias.

## Uso de @Injectable
* Servicio básico con @Injectable
```ts
import { Injectable } from '@angular/core';

@Injectable({
  providedIn: 'root', // Disponible en toda la aplicación
})
export class LoggingService {
  log(message: string): void {
    console.log(message);
  }
}
```

* **Inyección de dependencias en un servicio**, Un servicio puede depender de otros servicios, y Angular se encarga de inyectarlos automáticamente:
```ts
@Injectable({
  providedIn: 'root',
})
export class NotificationService {
  constructor(private loggingService: LoggingService) {}

  notify(message: string): void {
    this.loggingService.log(`Notification: ${message}`);
  }
}
```

* **Configuración de ámbito específico**, El servicio puede estar disponible solo en un módulo en lugar de toda la aplicación:
```ts
@Injectable({
  providedIn: SomeFeatureModule,
})
export class FeatureService {
  constructor() {}
}
```

## Uso de `@Optional` y `@Self`
* `@Optional`: Un decorador que marca una dependencia como opcional. Si Angular no encuentra la dependencia, no arrojará un error, sino que inyectará `null`.

* `@Self`: Un decorador que fuerza la resolución de una dependencia dentro del injector local (el componente o módulo donde se declara la dependencia). Ignora los injectores padres al buscar la dependencia.

Ambos son parte del sistema de Inyección de Dependencias (DI) de Angular.

### ¿Para qué sirven?
* `@Optional`
  * Permite que las dependencias no sean estrictamente necesarias.

  * Evita errores en tiempo de ejecución si un servicio no está registrado.

  * Facilita la creación de componentes o servicios reutilizables que pueden funcionar con o sin ciertas dependencias.

* `@Self`
  * Controla la ubicación de las dependencias para evitar usar servicios heredados de inyectores padres.

  * Asegura que los servicios se resuelvan únicamente desde el contexto local, promoviendo independencia.

### ¿Qué resuelven?
* `@Optional`
  * Problema: Cuando una dependencia no está registrada, Angular lanza un error. Esto puede ser problemático en escenarios donde una dependencia es opcional.

  * Solución: @Optional permite manejar la ausencia de una dependencia y tomar decisiones alternativas (como usar un valor por defecto o no ejecutar cierta lógica).

* `@Self`
  * Problema: Por defecto, Angular resuelve dependencias buscando en el inyector local y luego en los inyectores padres. Esto puede causar conflictos si se desea un servicio específico del contexto local.

  * Solución: @Self fuerza a Angular a buscar únicamente en el inyector local, evitando conflictos o dependencias accidentales de inyectores padres.

### ¿Cómo lo resuelven?
* `@Optional`, Cuando se usa `@Optional`, Angular:
  * Busca la dependencia en el inyector (local y padres).

  * Si no la encuentra, inyecta `null` en lugar de lanzar un error.

* Ejemplo:
```ts
@Injectable({
  providedIn: 'root',
})
export class LoggerService {
  log(message: string): void {
    console.log(message);
  }
}

@Component({
  selector: 'app-example',
  template: `<p>Ejemplo con @Optional</p>`,
})
export class ExampleComponent {
  constructor(@Optional() private logger: LoggerService) {
    if (this.logger) {
      this.logger.log('Logger disponible');
    } else {
      console.warn('Logger no está disponible');
    }
  }
}
```
Resultado:
  * Si `LoggerService` está registrado, se usa para registrar mensajes.

  * Si no está registrado, no genera un error y muestra un mensaje de advertencia.

* **`@Self`**, Cuando se usa `@Self`, Angular:
  * Resuelve la dependencia únicamente en el inyector local.

  * Si no encuentra la dependencia en el contexto local, lanza un error.

* Ejemplo:
```ts
@Component({
  selector: 'app-example',
  template: `<p>Ejemplo con @Self</p>`,
  providers: [{ provide: 'LocalService', useValue: 'Soy local' }],
})
export class ExampleComponent {
  constructor(@Self() @Inject('LocalService') private localService: string) {
    console.log(`Servicio inyectado: ${this.localService}`);
  }
}
```
Resultado:
  * La dependencia `LocalService` se resuelve desde el inyector local.

  * Si se intenta resolver desde un inyector padre, Angular lanza un error.

### Ventajas
* `@Optional`
  * Mejora la flexibilidad de los componentes o servicios.

  * Reduce errores en tiempo de ejecución para dependencias opcionales.

  * Facilita el uso de servicios opcionales en entornos de pruebas o configuraciones múltiples.

* `@Self`
  * Controla la fuente de las dependencias, mejorando la modularidad.

  * Evita dependencias accidentales desde inyectores padres.

  * Asegura independencia en módulos o componentes específicos.

### Buenas prácticas
* Usar @Optional solo cuando sea realmente necesario.

  * No marques dependencias críticas como opcionales.

  * Implementa comportamientos alternativos claros para cuando no esté disponible.

* Usar @Self en componentes o servicios que necesiten aislamiento.

  * Ideal para evitar conflictos en entornos con jerarquías complejas de inyectores.

* Pruebas unitarias:

  * Cuando uses @Optional, prueba escenarios con y sin la dependencia registrada.

  * Para @Self, valida que el servicio no dependa de inyectores padres.
